    High Availability for Hosted Control Planes¶

    Source: Red Hat OpenShift Container Platform 4.19/4.20 Documentation
    Last Updated: 2025-01-09

    1. Overview¶

    You can maintain high availability (HA) of hosted control planes by implementing:

    Action Description
    Recover etcd members Fix individual failing etcd pods
    Backup/Restore etcd Point-in-time recovery of cluster state
    Disaster Recovery Full cluster recovery to same or new management cluster

    Architecture: Control Plane Decoupling¶

    ┌─────────────────────────────────────────────────────────────────┐
│                    MANAGEMENT CLUSTER                            │
│  ┌─────────────────────────────────────────────────────────────┐│
│  │               HyperShift Operator                            ││
│  │  ┌─────────────────┐  ┌─────────────────┐                   ││
│  │  │  HostedCluster  │  │    NodePool     │                   ││
│  │  └────────┬────────┘  └────────┬────────┘                   ││
│  └───────────┼────────────────────┼─────────────────────────────┘│
│              │                    │                              │
│  ┌───────────▼────────────────────▼─────────────────────────────┐│
│  │         HOSTED CONTROL PLANE NAMESPACE                        ││
│  │  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌──────────────────┐   ││
│  │  │ etcd-0  │ │ etcd-1  │ │ etcd-2  │ │ kube-apiserver   │   ││
│  │  └─────────┘ └─────────┘ └─────────┘ └──────────────────┘   ││
│  │  ┌──────────────────┐ ┌──────────────────┐                   ││
│  │  │ kube-controller  │ │ kube-scheduler   │                   ││
│  │  └──────────────────┘ └──────────────────┘                   ││
│  └──────────────────────────────────────────────────────────────┘│
└─────────────────────────────────────────────────────────────────┘
                              │
                    External DNS / API
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│                      DATA PLANE                                  │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐                            │
│  │ Worker  │ │ Worker  │ │ Worker  │  ◄── Workloads run here    │
│  │ Node 1  │ │ Node 2  │ │ Node 3  │      INDEPENDENT of        │
│  └─────────┘ └─────────┘ └─────────┘      management cluster    │
└─────────────────────────────────────────────────────────────────┘

    Key Insight: The control plane is decoupled from the data plane, providing resiliency. Workloads continue running even when the management cluster fails.

    2. Impact Matrix¶

    When Management Cluster Components Fail¶

    Failed Component Control Plane Impact Data Plane Impact
    Management API Cannot modify cluster configuration ✅ No impact - workloads run
    etcd (management) Cannot modify cluster configuration ✅ No impact - workloads run
    HyperShift Operator Cannot create/modify hosted clusters ✅ No impact - workloads run
    Ingress Controller API access may be affected ✅ No impact - workloads run
    Entire Management Cluster Hosted cluster in read-only state ✅ No impact - workloads run

    When Hosted Control Plane Components Fail¶

    Failed Component Impact Recovery
    Single etcd pod Quorum maintained, auto-recovery Wait for automatic recovery
    Two etcd pods Quorum lost, cluster degraded Immediate intervention required
    All etcd pods Cluster unavailable Restore from backup
    kube-apiserver Cannot access hosted cluster API Pod auto-restarts
    kube-controller-manager Workloads not reconciled Pod auto-restarts

    3. etcd Cluster Health¶

    3.1 Check etcd Cluster Status¶

    In a highly available control plane, three etcd pods run as part of a StatefulSet.

    # Set control plane namespace
export CONTROL_PLANE_NAMESPACE="clusters-<hosted-cluster-name>"

# Check etcd pods status
oc get pods -n ${CONTROL_PLANE_NAMESPACE} -l app=etcd

# Expected output (healthy):
# NAME     READY   STATUS    RESTARTS   AGE
# etcd-0   1/1     Running   0          24h
# etcd-1   1/1     Running   0          24h
# etcd-2   1/1     Running   0          24h

    3.2 Check etcd Member Health¶

    # Log into an etcd pod
oc rsh -n ${CONTROL_PLANE_NAMESPACE} -c etcd etcd-0

# Inside the pod, check endpoint health
etcdctl endpoint health --cluster

# Expected output (healthy):
# https://etcd-0...:2379 is healthy: successfully committed proposal
# https://etcd-1...:2379 is healthy: successfully committed proposal
# https://etcd-2...:2379 is healthy: successfully committed proposal

# Check member list
etcdctl member list -w table

# Exit pod
exit

    3.3 Check etcd Database Size¶

    # Check database size (should be < 8GB)
oc rsh -n ${CONTROL_PLANE_NAMESPACE} -c etcd etcd-0 \
  etcdctl endpoint status --cluster -w table
    Metric Healthy Value Action if Exceeded
    DB Size < 8 GB Defragment or investigate
    Raft Term Stable High churn indicates issues
    Leader One leader Multiple indicates split-brain

    4. Recovering Unhealthy etcd¶

    4.1 Decision Tree¶

                     ┌──────────────────────┐
                 │  etcd pod unhealthy  │
                 └──────────┬───────────┘
                            │
              ┌─────────────┴─────────────┐
              │   How many pods failed?   │
              └─────────────┬─────────────┘
                    │               │
              ┌─────┴─────┐   ┌─────┴─────┐
              │  1 pod    │   │ 2+ pods   │
              └─────┬─────┘   └─────┬─────┘
                    │               │
                    ▼               ▼
         ┌──────────────────┐ ┌──────────────────┐
         │ Delete pod,      │ │ Restore from     │
         │ let it recreate  │ │ etcd backup      │
         └──────────────────┘ └──────────────────┘

    4.2 Recover Single Failing etcd Pod¶

    Use when: One etcd pod is failing but quorum (2/3) is maintained.

    # Set variables
export CONTROL_PLANE_NAMESPACE="clusters-<hosted-cluster-name>"
export FAILED_POD="etcd-1"  # The failing pod

# Step 1: Verify the failing pod
oc get pods -n ${CONTROL_PLANE_NAMESPACE} -l app=etcd

# Step 2: Delete the failing pod (it will be recreated)
oc delete pod ${FAILED_POD} -n ${CONTROL_PLANE_NAMESPACE}

# Step 3: Wait for pod to be recreated
oc get pods -n ${CONTROL_PLANE_NAMESPACE} -l app=etcd -w

# Step 4: Verify etcd cluster health
oc rsh -n ${CONTROL_PLANE_NAMESPACE} -c etcd etcd-0 \
  etcdctl endpoint health --cluster

    4.3 Recover Multiple Failing etcd Pods (Quorum Lost)¶

    Use when: Multiple etcd pods are failing and quorum is lost.

    ⚠️ WARNING: This procedure deletes etcd data. Only use when you have a backup or the data is already corrupted.

    # Set variables
export CONTROL_PLANE_NAMESPACE="clusters-<hosted-cluster-name>"

# Step 1: Scale down etcd StatefulSet to 0
oc scale -n ${CONTROL_PLANE_NAMESPACE} statefulset/etcd --replicas=0

# Step 2: Wait for pods to terminate
oc get pods -n ${CONTROL_PLANE_NAMESPACE} -l app=etcd -w

# Step 3: Delete the PVCs for failed members (keep etcd-0 if it has good data)
# ONLY delete PVCs for corrupted members
oc delete -n ${CONTROL_PLANE_NAMESPACE} pvc/data-etcd-1 pvc/data-etcd-2

# Step 4: Scale etcd back up
oc scale -n ${CONTROL_PLANE_NAMESPACE} statefulset/etcd --replicas=3

# Step 5: Wait for new pods and verify health
oc get pods -n ${CONTROL_PLANE_NAMESPACE} -l app=etcd -w

    5. etcd Backup and Restore (On-Premise)¶

    For hosted clusters on bare metal or on-premise environments.

    5.1 Taking an etcd Snapshot¶

    # Set variables
export CONTROL_PLANE_NAMESPACE="clusters-<hosted-cluster-name>"
export BACKUP_DIR="/tmp/etcd-backup-$(date +%Y%m%d-%H%M%S)"

# Step 1: Create backup directory
mkdir -p ${BACKUP_DIR}

# Step 2: Get the etcd client endpoint
ETCD_ENDPOINT=$(oc get pods -n ${CONTROL_PLANE_NAMESPACE} etcd-0 \
  -o jsonpath='{.status.podIP}'):2379

# Step 3: Take snapshot from etcd-0
oc exec -n ${CONTROL_PLANE_NAMESPACE} etcd-0 -c etcd -- \
  etcdctl snapshot save /var/lib/data/snapshot.db

# Step 4: Copy snapshot to local machine
oc cp ${CONTROL_PLANE_NAMESPACE}/etcd-0:/var/lib/data/snapshot.db \
  ${BACKUP_DIR}/snapshot.db -c etcd

# Step 5: Verify snapshot
oc exec -n ${CONTROL_PLANE_NAMESPACE} etcd-0 -c etcd -- \
  etcdctl snapshot status /var/lib/data/snapshot.db -w table

# Step 6: Store backup safely
echo "Backup saved to: ${BACKUP_DIR}/snapshot.db"

    5.2 Restoring from etcd Snapshot¶

    ⚠️ WARNING: Restoring etcd is a destructive operation. The cluster will be unavailable during restore.

    # Set variables
export CONTROL_PLANE_NAMESPACE="clusters-<hosted-cluster-name>"
export SNAPSHOT_FILE="/path/to/snapshot.db"

# Step 1: Pause the HostedCluster
oc patch hostedcluster <name> -n clusters --type=merge \
  -p '{"spec":{"pausedUntil":"true"}}'

# Step 2: Scale down etcd
oc scale -n ${CONTROL_PLANE_NAMESPACE} statefulset/etcd --replicas=0

# Step 3: Wait for pods to terminate
oc wait --for=delete pod/etcd-0 pod/etcd-1 pod/etcd-2 \
  -n ${CONTROL_PLANE_NAMESPACE} --timeout=120s

# Step 4: Delete all etcd PVCs
oc delete pvc -n ${CONTROL_PLANE_NAMESPACE} \
  data-etcd-0 data-etcd-1 data-etcd-2

# Step 5: Copy snapshot to a temporary location accessible by the restore job
# (This depends on your storage setup - using a PVC or ConfigMap)

# Step 6: Create restore job (see manifests/etcd-restore-job.yaml)

# Step 7: Scale etcd back up
oc scale -n ${CONTROL_PLANE_NAMESPACE} statefulset/etcd --replicas=3

# Step 8: Resume the HostedCluster
oc patch hostedcluster <name> -n clusters --type=merge \
  -p '{"spec":{"pausedUntil":null}}'

# Step 9: Verify cluster health
oc get hostedcluster <name> -n clusters

    6. etcd Backup and Restore (AWS)¶

    For hosted clusters on AWS with S3 storage.

    6.1 Taking an etcd Snapshot on AWS¶

    # Set variables
export CONTROL_PLANE_NAMESPACE="clusters-<hosted-cluster-name>"
export S3_BUCKET="your-etcd-backup-bucket"
export BACKUP_NAME="etcd-snapshot-$(date +%Y%m%d-%H%M%S)"

# Step 1: Take snapshot
oc exec -n ${CONTROL_PLANE_NAMESPACE} etcd-0 -c etcd -- \
  etcdctl snapshot save /var/lib/data/snapshot.db

# Step 2: Copy to S3 (if aws CLI is available in pod, or use oc cp + aws s3 cp)
oc cp ${CONTROL_PLANE_NAMESPACE}/etcd-0:/var/lib/data/snapshot.db \
  /tmp/snapshot.db -c etcd

aws s3 cp /tmp/snapshot.db s3://${S3_BUCKET}/${BACKUP_NAME}/snapshot.db

    6.2 Restoring from S3 Backup¶

    The restore process for AWS is similar to on-premise but uses S3 for snapshot storage.

    # Download snapshot from S3
aws s3 cp s3://${S3_BUCKET}/${BACKUP_NAME}/snapshot.db /tmp/snapshot.db

# Follow on-premise restore procedure using the downloaded snapshot

    7. Disaster Recovery with OADP¶

    For full cluster disaster recovery, use OpenShift API for Data Protection (OADP).

    7.1 When to Use OADP vs etcd Restore¶

    Scenario Use etcd Restore Use OADP
    etcd data corruption ✅ ✅
    Accidental resource deletion ✅ ✅
    Management cluster failure ❌ ✅
    Migrate to new management cluster ❌ ✅
    Full hosted cluster backup ❌ ✅

    7.2 OADP Backup/Restore¶

    See the following runbooks: - BACKUP-PROCEDURES.md - Complete backup steps - RESTORE-PROCEDURES.md - Complete restore steps - DR-PLAN.md - Full disaster recovery plan

    7.3 Quick OADP Backup¶

    # Install OADP and configure (one-time setup)
./scripts/01-install-oadp.sh

# Backup a hosted cluster
./scripts/02-backup-control-plane.sh <hosted-cluster-name> clusters

# Verify backup
./scripts/verify-backup.sh <backup-name>

    7.4 Quick OADP Restore¶

    # Restore to same management cluster
./scripts/04-restore-same-cluster.sh <backup-name>

# Restore to new management cluster
./scripts/05-restore-new-cluster.sh <backup-name>

    8. Quick Reference Commands¶

    Health Checks¶

    # Set namespace
export CONTROL_PLANE_NAMESPACE="clusters-<name>"

# Check all HCP pods
oc get pods -n ${CONTROL_PLANE_NAMESPACE}

# Check etcd specifically
oc get pods -n ${CONTROL_PLANE_NAMESPACE} -l app=etcd

# Check etcd cluster health
oc rsh -n ${CONTROL_PLANE_NAMESPACE} -c etcd etcd-0 \
  etcdctl endpoint health --cluster

# Check etcd member list
oc rsh -n ${CONTROL_PLANE_NAMESPACE} -c etcd etcd-0 \
  etcdctl member list -w table

# Check etcd database size
oc rsh -n ${CONTROL_PLANE_NAMESPACE} -c etcd etcd-0 \
  etcdctl endpoint status --cluster -w table

    HostedCluster Status¶

    # Check HostedCluster status
oc get hostedcluster -A -o wide

# Check HostedCluster conditions
oc get hostedcluster <name> -n clusters \
  -o jsonpath='{.status.conditions}' | jq

# Check NodePool status
oc get nodepool -n clusters

# Get hosted cluster kubeconfig
oc get secret <name>-admin-kubeconfig -n clusters \
  -o jsonpath='{.data.kubeconfig}' | base64 -d > /tmp/hc-kubeconfig

    Recovery Actions¶

    # Pause reconciliation
oc patch hostedcluster <name> -n clusters --type=merge \
  -p '{"spec":{"pausedUntil":"true"}}'

# Resume reconciliation
oc patch hostedcluster <name> -n clusters --type=merge \
  -p '{"spec":{"pausedUntil":null}}'

# Delete failing etcd pod (triggers recreation)
oc delete pod etcd-X -n ${CONTROL_PLANE_NAMESPACE}

# Scale etcd
oc scale -n ${CONTROL_PLANE_NAMESPACE} statefulset/etcd --replicas=N

# Force delete stuck pod
oc delete pod <pod-name> -n ${CONTROL_PLANE_NAMESPACE} --force --grace-period=0

    Troubleshooting¶

    # etcd logs
oc logs -n ${CONTROL_PLANE_NAMESPACE} etcd-0 -c etcd

# kube-apiserver logs
oc logs -n ${CONTROL_PLANE_NAMESPACE} -l app=kube-apiserver

# Events in control plane namespace
oc get events -n ${CONTROL_PLANE_NAMESPACE} --sort-by='.lastTimestamp'

# Must-gather for HCP
oc adm must-gather --image=quay.io/openshift/origin-must-gather:latest \
  --dest-dir=./must-gather-hcp -- /usr/bin/gather_hosted_cluster <name>
