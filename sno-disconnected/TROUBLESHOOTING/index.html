    SNO Disconnected Troubleshooting Guide¶

    Console Not Accessible from macOS via Tailscale¶

    Symptom: Cannot connect to console-openshift-console.apps.sno-disconnected.example.local from macOS when using Tailscale for connectivity.

    Troubleshooting Workflow¶

    Step 1: Verify DNS Resolution¶

    # Check if Tailscale MagicDNS can resolve the hostname
nslookup console-openshift-console.apps.sno-disconnected.example.local

# Check /etc/hosts for static entries
grep -i sno /etc/hosts

    Why: The .example.local domain is only configured in the libvirt network DNS on homelab-server. macOS won't resolve it unless: - Entry exists in /etc/hosts - A DNS server that knows about .example.local is configured

    Expected /etc/hosts entry: 

    198.51.100.60 api.sno-disconnected.example.local api-int.sno-disconnected.example.local oauth-openshift.apps.sno-disconnected.example.local console-openshift-console.apps.sno-disconnected.example.local

    Step 2: Verify Network Connectivity¶

    # Check Tailscale status and connection to homelab-server
tailscale status

# Ping the SNO node directly
ping -c 1 198.51.100.60

    Why: Even with correct DNS, traffic must route through Tailscale to homelab-server (192.0.2.107), then to the isolated network (198.51.100.0/24). Tailscale must be advertising the route.

    Step 3: Test Port Connectivity¶

    # Test HTTPS port (router/ingress)
nc -zv -w 5 198.51.100.60 443

# Test API port (kube-apiserver)
nc -zv -w 5 198.51.100.60 6443

    Why: Identifies which layer is failing: - Port 443 = OpenShift Router/Ingress (serves console, routes) - Port 6443 = Kubernetes API server

    Port 443 Port 6443 Meaning
    ❌ ✅ Router is down, API is up
    ❌ ❌ Node is down or network issue
    ✅ ✅ Both services running

    Step 4: Test HTTP Response¶

    # Test console URL with curl
curl -sk --connect-timeout 10 \
  https://console-openshift-console.apps.sno-disconnected.example.local \
  -o /dev/null -w "HTTP: %{http_code}, Time: %{time_total}s\n"

# Test with explicit IP resolution
curl -sk --connect-timeout 10 \
  --resolve "console-openshift-console.apps.sno-disconnected.example.local:443:198.51.100.60" \
  https://console-openshift-console.apps.sno-disconnected.example.local \
  -o /dev/null -w "HTTP: %{http_code}\n"

    Why: Distinguishes between DNS issues and actual service failures: - 000 = Connection failed (timeout, refused, network issue) - 200 = Success - 503 = Service unavailable (backend issue)

    Step 5: Check Cluster Operators (from homelab-server)¶

    # SSH to homelab-server where cluster access is available
ssh lab-user@homelab-server.example.com

# Set kubeconfig
export KUBECONFIG=/home/lab-user/sno-disconnected/auth/kubeconfig

# Check all cluster operators for issues
oc get co | grep -v 'True.*False.*False'

# Specifically check ingress operator
oc get co ingress

    Why: Shows which operators are unhealthy. Pattern True False False = healthy. Look for: - AVAILABLE=False = Service not working - PROGRESSING=True = Operator is updating/recovering - DEGRADED=True = Operator has errors

    Step 6: Check Router Pod Status¶

    # Check router pods
oc get pods -n openshift-ingress

# Check router events
oc get events -n openshift-ingress --sort-by='.lastTimestamp' | tail -20

    Why: The router pod serves all .apps.* traffic. Common issues: - 0/1 Running with restarts = Container crashing - Pending = Scheduling issue - ImagePullBackOff = Can't pull image (disconnected issue)

    Step 7: Check Router Logs via crictl (bypass kubelet cert issues)¶

    # SSH to SNO node directly
ssh core@198.51.100.60

# Find router container
sudo crictl ps -a | grep router

# Get logs from router container
CONTAINER_ID=$(sudo crictl ps -a | grep router | head -1 | awk '{print $1}')
sudo crictl logs $CONTAINER_ID 2>&1 | head -100
sudo crictl logs $CONTAINER_ID 2>&1 | tail -50

    Why: Sometimes oc logs fails with certificate errors. Using crictl directly on the node bypasses the kubelet API and reads container logs from the runtime.

    Step 8: Check OpenShift API Server¶

    # Check openshift-apiserver pods
oc get pods -n openshift-apiserver

# Check openshift-apiserver operator
oc get co openshift-apiserver

# Check Route API service availability
oc get apiservice v1.route.openshift.io

    Why: The router depends on the Routes API (routes.route.openshift.io). If the OpenShift API server is unhealthy, the router can't sync routes and HAProxy won't start.

    Step 9: Check Node Resources¶

    # SSH to SNO node
ssh core@198.51.100.60

# Check memory
free -h

# Check disk space
df -h / /var

# Check CPU load
uptime

# Check for OOM kills
sudo dmesg | grep -i "out of memory" | tail -5

    Why: SNO runs all control plane components on a single node. Resource exhaustion causes cascading failures: - High load average (>8 on 8 vCPU) = CPU contention - Low available memory = Risk of OOM kills - Full disk = etcd/kubelet failures

    Common Root Causes¶

    1. Router Can't Sync Routes (401 Unauthorized)¶

    Symptom: 

    failed to list *v1.Route: the server is currently unable to handle the request

    Cause: OpenShift API server returning 401 errors for aggregated API calls.

    Resolution: Usually self-heals. Wait for the openshift-apiserver to stabilize. Check: 

    oc get co openshift-apiserver
oc get apiservice v1.route.openshift.io

    2. HAProxy Socket Missing¶

    Symptom: 

    can't scrape HAProxy: dial unix /var/lib/haproxy/run/haproxy.sock: no such file or directory

    Cause: HAProxy process never started because router couldn't sync routes.

    Resolution: Fix the underlying Routes API issue. Router will auto-recover.

    3. High Node Load¶

    Symptom: Load average consistently >8 on 8 vCPU node.

    Cause: Resource contention on SNO. Too many pods or operators competing.

    Resolution: - Increase VM resources (vCPU, RAM) - Reduce workloads - Check for runaway pods: oc adm top pods -A --sort-by=cpu | head -20

    Quick Recovery Commands¶

    # Force router pod restart (last resort)
oc delete pod -n openshift-ingress -l ingresscontroller.operator.openshift.io/deployment-ingresscontroller=default

# Check if cluster is recovering
watch -n5 'oc get co | grep -v "True.*False.*False"'

# Verify console is accessible
curl -sk https://console-openshift-console.apps.sno-disconnected.example.local -o /dev/null -w "%{http_code}\n"

    Architecture Reference¶

    macOS (Tailscale: 100.64.50.3)
    │
    │ Tailscale tunnel
    ▼
homelab-server.example.com (192.0.2.107 / Tailscale: 100.106.93.76)
    │
    │ Bridge to isolated network
    ▼
sno-disconnected (198.51.100.60)
    ├── Port 6443: kube-apiserver
    ├── Port 443: router (HAProxy) ← serves console, routes
    └── Port 22: SSH (core user)

    Key: Traffic flows macOS → Tailscale → homelab-server → bridge → SNO node.
